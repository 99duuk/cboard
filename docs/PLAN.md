# Cboard 구현 계획

작성일: 2026-10-14. v0.1.0 구현 완료. 실제 수행 범위와 한계는 [검증 기록](VERIFICATION.md)을 따른다.

목표는 [SPEC.md](SPEC.md)의 F01~F08을 충족하는 작은 통합 Command Center다. 단계마다 동작하는 결과를 남기고, 다음 단계는 앞 단계의 계약을 사용한다.

## 0. 사전 조사 — 완료

- [x] 현행 계정 설정과 설치된 Codex CLI 0.162.1 확인.
- [x] 해당 실행 파일에서 experimental 포함 JSON Schema 생성. 임시 조사 경로에만 저장.
- [x] 기존 5계정 daemon에 WebSocket over Unix socket으로 연결.
- [x] 비보관 interactive 목록 전체 716개 pagination 확인.
- [x] 계정별 최근 대화의 metadata와 최근 3 turn 조회.
- [x] 조회 전후 loaded ID 집합이 변하지 않는 것을 확인.
- [x] 익명화된 결과와 제약을 [DISCOVERY.md](DISCOVERY.md)에 기록.

이것은 데이터 접근 가능성 검증이다. 완성된 앱·TUI·재개 기능 시험은 아니다.

## 1. 데이터 계약과 조회 코어

대상: pyproject.toml, config.py, models.py, sources/rpc.py, sources/codex.py, services.py, 대응 tests/fixtures.

작업:

1. 프로젝트 전용 가상환경, Python 3.11+ 기준, 의존성 lockfile을 만든다. 먼저 websockets만 연결한다.
2. 계정 설정 5개를 선언적으로 읽는다. 계정 id와 표시 이름을 분리한다.
3. 계정당 기존 소켓 하나에 연결하고, JSON-RPC 수신 루프/요청 ID/timeout/재연결을 구현한다.
4. 비보관 interactive 목록의 모든 페이지와 loaded 목록을 합친다. API 응답을 UI와 무관한 모델로 변환한다.
5. source=cli만 필터링하지 않고, 부모·출처로 subagent를 기본 제외한다. 목록에 없는 loaded 대화도 확인한다.
6. 관찰 전용 연결로 각 상태를 실제 원본 Command Center와 대조한다. 대기 상태는 mock fixture와 이후 지정한 시험 대화로 확인한다.
7. thread/items/list를 먼저 검증하고 최근 메시지 로더를 선택한다. `preview`를 마지막 요청으로 사용하지 않는다.
8. 진단용 `cboard list --json`을 제공한다. JSON 출력도 UI와 같은 정규화 모델을 사용한다.

완료 조건:

- 실제 5계정의 페이지를 읽고, 같은 시점의 account별 개수·source·status를 대조할 수 있다.
- UI를 import하지 않고 fixture로 상태 변환·pagination·중복 ID·실패 계정을 시험한다.
- 조회 경로에서 허용한 RPC 외의 메서드는 호출되지 않는다. fake server 로그로 확인한다.
- disconnect/reconnect의 응답 역전, 알 수 없는 필드·상태, method not found를 처리한다.

## 2. 통합 화면

대상: ui/app.py, ui/widgets.py, ui/theme.tcss, services.py의 표시용 조회, CLI 진입점.

작업:

1. Textual을 추가하고 프로젝트별 목록과 오른쪽 상세 패널을 구성한다.
2. 상태 필터, 계정 필터, 제목/경로 검색, 그룹 전환을 연결한다.
   F01/F02의 기본 목록은 상태보다 날짜를 우선한 전체 최근순이다. `g`로 전체 최근순/프로젝트별/계정별을 전환하고 그룹 내부도 최근순으로 유지한다.
3. 계정 조회는 병렬, 상세는 선택 시 지연 로딩한다. 선택 변경 시 이전 응답을 무시한다.
4. 3초 loaded 상태 확인/15초 목록 조정을 구현하고 선택·스크롤을 안정적인 키로 유지한다.
5. 연결 장애·오래된 값·부분 개수를 표시한다. 최소 화면에서는 목록/상세를 전환한다.

완료 조건:

- 사진에서 필요한 제목·상태·계정·프로젝트·모델·마지막 메시지를 한 화면에서 파악할 수 있다.
- 716개 및 합성 2,000개 metadata로 검색·선택 중 UI가 멈추지 않는다.
- 시험용 로컬 서버에서 첫 계정 목록 2초 이내, 전체 5계정 metadata 5초 이내를 초기 목표로 측정한다. 실측과 환경을 함께 기록하고 근거 없이 목표 충족을 주장하지 않는다.
- 80×24 / 120×35 / 160×45에서 한글·긴 경로·Markdown·상태 색상·키보드 이동을 확인한다.
- Textual Pilot로 필터→선택→느린 상세 응답→다른 항목 선택 시 잘못된 상세가 나오지 않는 시나리오를 검증한다.

## 3. 숨김·선택 저장

대상: state.py, F04/F06 UI 동작, state 관련 tests.

작업:

1. 숨김, 다중 선택, 마지막 필터/그룹을 로컬 state로 저장한다.
2. 계정별 metadata cache와 조회 시각을 저장한다. 대화 본문 전체는 cache에 넣지 않는다.
3. file lock + read-modify-write + atomic replace로 여러 실행의 상태 충돌을 막는다.
4. 손상된 JSON, 알 수 없는 schema_version, 사라진 계정/대화의 선택을 명시적으로 처리한다.

완료 조건:

- 7개 중 2개 숨김·5개 선택 → 종료/강제종료 → 재실행에서 선택 5개가 남는다.
- 숨기기는 원래 Codex의 archive·대화 파일·실행 상태를 바꾸지 않는다.
- 저장 도중 중단돼도 기존 정상 파일이 깨지지 않는다. 둘이 동시에 수정해도 관련 없는 선택·숨김 변경이 유실되지 않는다.

## 4. iTerm2 재개

대상: terminals/command.py, terminals/iterm.py, services.py의 재개 판단, UI 재개 동작.

작업:

1. 먼저 argv/env/cwd만 만드는 ResumeSpec과 명령 복사를 완성한다.
2. iTerm2 Python API 사용 가능 여부를 확인한다. 현재 환경에서는 비활성이므로 내장 AppleScript를 연결했다. 연동이 차단되면 읽기 UI와 명령 복사는 계속 동작한다.
3. 매번 새 iTerm2 탭을 생성하고 생성된 탭을 선택한다. 원래 thread ID·계정·프로젝트 폴더를 그대로 재개한다.
4. 기존 탭 검색·재사용·표시자 관리 로직은 제거한다.
5. 숨김/보관/경로 유효성/실행 중 상태를 재검사하고, 단일·다중 재개와 부분 실패 처리를 연결한다.
6. 재개 프로세스가 원래 계정으로 초기화되고 동일한 대화를 가리키는지 확인한다. spawn 성공만으로 복구 완료라고 표시하지 않는다.
7. F05의 iTerm2 연동 실패는 개별 항목 오류와 구분한다. 첫 자동화 실패에서 batch를 중단하고 현재 실행의 자동 열기를 비활성화하며, 선택과 명령 복사를 유지한다. 대기 중 요청의 재시도 차단과 공용 자동화 잠금을 fixture로 검증한다. 실제 탭 생성·닫기 반복 시험은 수행하지 않는다.
8. 계정별 프로필·배경색 설정을 Account → ResumeSpec → ItermLauncher에 연결한다. 프로필은 이름으로 새 탭/창을 만들고 배경색은 새 탭의 실행 명령에서 적용한다. 기존 셸 매핑을 로컬 설정에 반영하고 저장된 iTerm2 프로필 존재·명령 인용·AppleScript 문법을 검증한다.

완료 조건:

- 사용자가 지정한 시험용 대화로 각 계정의 정확한 thread가 재개된다. 자동 프롬프트가 전송되지 않는다.
- 공백·따옴표·`$()`·백틱이 포함된 경로를 실행 구문으로 해석하지 않는다. argv/env 단위 테스트와 무해한 fixture 경로로 확인한다.
- 같은 프로젝트의 서로 다른 두 계정, 같은 계정의 서로 다른 두 thread가 섞이지 않는다.
- 실행 중 중복 입력은 UI busy guard로 막고 자동화 요청은 직렬화한다. 완료 후 같은 대화를 다시 열면 새 탭이 생긴다.
- API 비활성·닫힌 탭·사라진 cwd·일부 계정 실패에서 다른 선택은 정상 처리된다.
- CLI 출처와 앱/IDE 출처 대화의 재개를 각각 확인한다.

## 6. 명시적 단일 대화 삭제

F07 대상: deletion.py, state.py의 선택·숨김 정리, UI 확인창, CLI에서의 서비스 주입.

- 기존 조회 연결의 allowlist는 유지하고 삭제 전용 연결에서 `thread/delete` 한 메서드만 추가한다.
- 비보관/보관 하위 대화 pagination과 로드된 임시 하위 대화의 부모 관계를 확인한다. 삭제 직전에 다시 검사해 확인창과 범위가 같고 모든 대상이 idle/notLoaded인 경우만 요청한다. Ready는 로드된 상태여도 허용하며 실제 실행·승인 대기는 거절한다.
- `Delete` → 계정·대화·범위 확인(취소에 초기 포커스) → 화살표로 영구 삭제 선택 → Enter 실행의 흐름을 연결한다. 확인어 입력은 없다. 취소/실패 시 선택은 유지하고 성공한 대상만 선택·숨김에서 제거한다.
- Unix WebSocket fixture에서 계정별 ID 분리, root/하위 대화 로드 차단, 범위 변경, 응답 유실을 검증한다. 실제 사용자 서버에는 삭제를 시험하지 않는다. 넓은 화면·80×24에서도 취소/확인 버튼을 조작할 수 있어야 한다.

## 7. 반복 갱신 성능 개선

F09/T26~T28 대상: models.py, services.py, sources/codex.py, ui/app.py.

- 5계정·700/2,000행·120×35 합성 데이터의 변경 전후를 같은 `scripts/benchmark.py`로 측정한다. 본문과 실제 계정을 사용하지 않는다.
- 변경 없는 행 재생성·metadata 저장·중복 저장 확인 조회를 줄이고, 실제 변경과 재개 직전 검사를 회귀 시험한다. 추가 의존성이나 상주 프로세스를 도입하지 않는다.
- 임시 state/cache에서 실제 5계정 읽기만 수행한 단일 표본은 합성 측정과 따로 기록한다. native 탭 생성·닫기·원본 세션 쓰기는 검증 목적으로 실행하지 않는다.
- F03 요청 → 답변 순서를 적용하고 샘플 화면을 재생성한다. 측정 환경·반복 횟수·한계와 전체 시험 결과를 VERIFICATION.md에 기록한다.
